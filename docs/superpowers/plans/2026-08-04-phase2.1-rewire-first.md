## 0. Why the bottom-up order was wrong, and the harness flaw that hid it

My reverse-dependency order assumed the plugin was two clean layers — skills on top,
compute underneath — so compute could move out from the bottom. **It isn't.** The
SKILL.md files are executable content, and they reach directly into the "dashboard-only"
compute:

- `skills/viva-cite-bands/SKILL.md:41,192,219,263,283,295` — six inline
  `from viva_superpowers.band_provenance import bands_missing_provenance / set_band_provenance`.
  `band_provenance` is skill-facing, not dashboard-only.
- `viva_superpowers/seed_from_followup.py:543` — `from .study_verdict import roll_up_verdict`.
  `seed_from_followup` is skill-facing (`/viva-study seed-from-followup`) and stays, so
  moving `study_verdict` to the workbench would recreate the plugin→workbench cycle that
  Phase 0 removed.
- `rigor` (via `report_linter`), `study_status` (via `study_verdict`), `hypotheses` (via
  `rigor`) inherit the block. **None of the old 2.1b could move.**

### The harness flaw — stated precisely, because it has now bitten three times

The Phase 2.0 harness *did* grep `skills/`. The defect was not coverage, it was
**classification**: §4 was labelled "SKILL.md prose" and I treated every hit as
documentation needing a wording edit. A SKILL.md is a program. `from viva_superpowers.X
import Y` inside one is a **code consumer with exactly the weight of a `.py` file**, and
`python -m viva_superpowers.X` is a **CLI consumer**. I only ever grepped skills for the
`python -m` form, which is why 40+ inline-import sites were invisible.

Same root cause each time:
1. **`package_audit`** — self-scan scoped to `viva_superpowers/ skills/ templates/`, so
   `scripts/audit-pbg-repo.py:5` was never seen.
2. **`refresh_viz`** — the drift guard existed but never ran in CI, so "guarded" was
   assumed rather than verified.
3. **`band_provenance` / `study_verdict`** — skill hits classified as prose.

**Harness fix (mandatory checklist item, §5):** the plugin's own repo is scanned *whole*,
and `skills/**/SKILL.md` is scanned for **three** consumer classes — inline imports,
`python -m`, and prose — with inline imports and `python -m` ranked as **hard blockers**,
never as doc edits.

### Cost of a new endpoint: low and formulaic
`api/app.py` is one `create_app()` factory with 215 routes, no `APIRouter`, no
`include_router`. A new endpoint is: (1) a builder in a `lib/*_views.py` returning
`(dict, int)`, (2) optionally a pydantic model in `lib/models.py`, (3) ~10 lines of
`@app.post(...)` inside `create_app()` — which **must be added above the catch-all SPA
route `GET /{rel:path}`**, the last route in the file. CSRF/origin middleware auto-guards
every non-GET. So the ~10 new endpoints across 2.1e–2.1h are real but cheap work; the
expensive part is the equivalence testing (§5), not the plumbing.

### ⚠️ PARTIAL — endpoint exists but not for the skill's exact op
- `study_narrative add-literature-anchor` — `POST /api/study-narrative-set`
  (`api/app.py:3389`) is a **set-leaf-at-path** writer, and `literature_anchors` *is* an
  allowed root (`lib/metadata_mutations.py:34-41`). So the data is reachable, but appending
  requires the caller to GET the study, append client-side, and PUT the whole list back —
  losing the field validation `viva_superpowers.study_narrative.add_literature_anchor`
  performs. **Prefer a sibling append route over GET-append-PUT**, so the validation moves
  server-side instead of being dropped.
- `study_findings` (auto/dry-run) — `/api/finding` exists for single findings; the
  `--auto` generation pass does not. **Needs `POST /api/study-findings-generate`.**
- `investigation_close` — `/api/investigation-set-status` sets status; the close
  *mechanic* (the multi-step checklist at `viva-investigation/SKILL.md:576`) does not
  exist. **Needs `POST /api/investigation-close`.**
- `study_verify` — `/api/study-observable-check` + `/api/study-readouts` cover parts;
  full spec verification does not. **Needs `POST /api/study-verify`.**
- `expert_search.search_expert_docs` — `/api/expert-doc` fetches one doc; there is no
  search. **Needs `GET /api/expert-search?q=`.**

no external consumer, moving it is mechanical and the *only* risk is the workbench's own
twin-merge. Batching lets each twin-merge be reviewed against a stable plugin. If 2.1k
proves too large in practice, split it along the same slice lines as the rewires
(navigation / report / cite-bands / study), **never** along the dependency DAG — that was
the failed premise.

**Ordering rationale:** 2.1b first because it needs *zero* new server code. 2.1c is
independent of everything (process-bigraph only). Then ascending by new-endpoint count.
2.1i/2.1j last because they are the pre-server bootstrap ops and force a new install
dependency (§5).

### 🚩 `paths` — recommend adding to the core, do NOT rewire (saves 5 sites)
`viva-report:40` and `viva-investigation:120` do
`eval "$(python -m viva_superpowers.paths --env --workspace "$WORKSPACE_ROOT")"` — this
runs **first**, to establish the shell environment, before anything else exists. A `vwb
paths --env` verb is shape-identical, but it makes **`vivarium-workbench` (FastAPI +
uvicorn + xarray + zarr) a hard install requirement for every skill user**, including
those doing pure-CLI work. `paths` is 141 LOC over `workspace_paths` (203, already
staying). **Ruling: add `paths` to the stay-in-plugin core.** Kills 5 of the 76 sites for
free and avoids a heavyweight dependency shift.

### 🚩 `seed_from_followup` → `study_verdict` must be severed, not rewired
`seed_from_followup.py:543`'s `from .study_verdict import roll_up_verdict` is a *lazy,
function-local* import, so it is cheap to cut — but it must be cut **before** 2.1k moves
`study_verdict`, or the cycle returns. Two options, decide in 2.1g:
(a) `seed_from_followup` also becomes server-side (it already has
`POST /api/study-seed-followup`), so both move — **preferred**; or
(b) inline the ~10-line verdict predicate into `seed_from_followup`, accepting one
duplicated rule. Take (a) unless the endpoint proves not to cover the skill's use.

### 🚩 The `viva-server` orphan scan — narrowed, but still real
`skills/viva-server/SKILL.md:38` scans `~/.pbg/servers/*.json` for orphaned records (dead
PID or vanished worktree). `POST /api/workspaces/cleanup-stale` (`api/app.py:6558`) already
does exactly this unlinking — so this is **less missing than I first flagged**. But the
endpoint is served *by a running server*, and the operation's entire purpose is to run when
servers are dead. So: repoint the skill to `/api/workspaces/cleanup-stale` for the common
case (some server alive), and keep a client-side path for the all-dead case. The dedup
query (`workspace_catalog.find_duplicates_for_path`) has no endpoint and no CLI — it needs
`vwb catalog duplicates-for-path`. Settle in 2.1i.

### 🚩 Rewire-first raises the floor for `viva-navigate`, `viva-cite-bands`, `viva-biology-forward`
All three are in-process today and become server-requiring. That is the *intended* trade
(it is what makes the compute movable), but it is a real UX change: three skills that
worked on a bare checkout now need `/viva-workbench start` first. Every rewire increment
must add the URL-resolution preflight and a clear error — and must **not** add an inline
fallback, which would preserve the coupling the increment exists to remove.

### Not blockers

independent of the workbench entirely, and 2.1c can land any time.
